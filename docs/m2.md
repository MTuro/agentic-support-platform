# LoopBack API and PostgreSQL (M2)

The public API persists conversations, both messages of every completed turn,
synthetic tickets and a durable escalation queue. All customer routes require a
customer bearer token and check conversation ownership. Analytics and the queue
require an operator bearer token. Identity comes exclusively from server-side
configuration. This is local demo authentication, not a production identity provider.

## Local startup

Use Node 24 LTS (or 22), Python 3.12, the agent environment from README, and local
Ollama with the documented models. PostgreSQL 18.4 was used for acceptance.
The npm lockfile pins API dependencies. From the repository root:

```bash
npm --prefix apps/api ci
npm --prefix apps/api run demo:env
npm --prefix apps/api run db:local
```

`db:local` starts an actual PostgreSQL binary from the development-only
`embedded-postgres` dependency on port 55432. It binds to 127.0.0.1 and creates
`.data/postgres`, a generated password, and `.data/database.env`. No system users
or system installation are changed. Keep that terminal running. Ctrl-C stops the
database and preserves its data. The package needs its symlink hydration install
script; if npm 12 reports it as blocked, run
`npm --prefix apps/api install-scripts approve @embedded-postgres/linux-x64`
and reinstall. Alternatively use your own local PostgreSQL and set `DATABASE_URL`.
Use a writable npm cache (`--cache /tmp/orbitdesk-npm`) if the default is read-only.

In a second terminal, activate the Python environment and load your `.env` with
`set -a; source .env; set +a`, including a generated `AGENT_SERVICE_TOKEN`. Then:

```bash
source .data/database.env
source .data/api.env
make ingest
make agent
```

In a third terminal, load the same environment and run:

```bash
source .data/database.env
source .data/api.env
npm --prefix apps/api run migrate
npm --prefix apps/api run seed
npm --prefix apps/api start
```

`migrate` applies ordered SQL files atomically under a PostgreSQL advisory lock,
recording SHA-256 checksums. Reapplication is safe; editing an applied migration
fails. Add a new migration to change an existing database. Startup never performs
implicit schema changes. The seed is repeatable and does not overwrite tickets.
It gives `TKT-1001` to `demo-alice` and `TKT-1002` to `demo-bob`.
`demo:env` generates distinct random customer and operator tokens in ignored
`.data/api.env` with mode 0600 and preserves existing credentials. Keep the
internal service token separate. `.env.example` documents manual configuration.

The API listens on `127.0.0.1:8000`. `PORT` can select another port; the agent uses
`AGENT_URL` (default `http://127.0.0.1:8001`). `AGENT_TIMEOUT_MS` defaults to 90000
and is bounded at 120000. `/health/live` checks the process, `/health/ready` checks
the relational conversation store; agent dependency failures remain separate.

## Implemented contract

The generated, validated [OpenAPI](../apps/api/openapi.json) is also available at
`GET /openapi.json`. Request bodies reject extra fields. Invalid path/header
parameters return 400; invalid JSON body values return 422. Missing or invalid
authentication returns 401, a wrong role returns 403, and another customer's
conversation is indistinguishable from a missing conversation (404).

| Route | Behavior |
| --- | --- |
| `POST /api/conversations` | Customer, `{}`, 201 with ID, timestamp and empty messages |
| `POST /api/conversations/{id}/messages` | Customer, `{content}` (1–4000 nonblank characters), required UUID `Idempotency-Key`, 201 with persisted assistant message |
| `GET /api/conversations/{id}` | Customer, 200 with ordered user/assistant messages, citations, route, reason, ticket snapshot and timestamps |
| `GET /api/operator/analytics` | Operator, counts of conversations/messages/escalations, and escalations per completed turn |
| `GET /api/operator/escalations` | Operator, oldest 100 durable queue records, including conversation and assistant message IDs, reason and status |

For a message request, generate a UUID once and reuse it for retries. Equal key
and content in the same conversation return the exact saved response. Reusing a
key for different content returns 409. Keys are scoped to conversations; UUID
case is normalized. Concurrent turns acquire a row lock, with a three-second
lock timeout returning retryable 409. Different conversations can progress
independently. Retry a busy conversation after the in-flight request finishes.

The API selects tickets by authenticated owner from PostgreSQL and sends only
that snapshot in the authenticated internal agent request. Python uses a fresh
request-scoped ticket store, never merging it with the standalone M1 fixture.
An empty list authorizes no tickets. The browser cannot supply ticket context.
Unknown and foreign tickets both yield `ticket_not_found`. The standalone M1
internal request without a `tickets` field still uses its synthetic fixture;
keep the service token private and never expose that internal API to browsers.

The agent client validates bounded response bytes, JSON structure and route
invariants before persistence. A ticket response must match an authorized
snapshot. One retry is allowed for transport or HTTP 5xx errors, within one total
request deadline. Invalid contracts, auth failures and oversized responses fail
without retry. A transport failure returns sanitized 503 and rolls back the
entire turn. A normal agent uncertainty/dependency decision returns 201 and
persists a human escalation, matching the agent contract.

Both messages, the idempotency record and any escalation commit in one
transaction. No partial user message or orphan escalation remains after a failed
write. The API holds the conversation lock while awaiting the agent; this favors
simple ordering over throughput. History is stateless for agent reasoning in M2;
messages persist for clients, but are not sent as conversational model context.

JSON request logs contain only generated/validated correlation UUID, status,
latency and event name. Errors do not echo SQL, credentials or user content.
`X-Request-ID` propagates across API and agent; invalid IDs are replaced.

## Verification

Keep PostgreSQL running and load the environment above:

```bash
make test
make lint
make typecheck
TEST_DATABASE_URL="$DATABASE_URL" npm --prefix apps/api test
npm --prefix apps/api run lint
npm --prefix apps/api run typecheck
npm --prefix apps/api run openapi
npm --prefix apps/api run smoke
```

Tests require real PostgreSQL, create a randomly named isolated schema, and drop
only that schema afterward. They never truncate shared application tables. A
local HTTP agent double is confined to integration tests to reproduce timeout,
malformed response, transport failure, ownership checks and retry behavior.
The smoke requires the actual Python/Ollama/Chroma stack and makes four real
requests: cited FAQ, owned ticket, foreign ticket and human request. It verifies
replays, history, authorization and the persisted rows/queue. It saves IDs in
ignored `.data/m2-smoke.json`. Stop and restart the API, then run:

```bash
npm --prefix apps/api run smoke -- --verify
```

Acceptance on 2026-10-27: Python 43 tests plus nine subtests; API 12 tests;
Python and API lint/type checks; generated OpenAPI validation; four real smoke
cases with zero failures; eight messages and two durable escalations; all eight
message IDs survive API restart. The FAQ took about 35 seconds on CPU in this
run. These are observed checks, not a production performance benchmark.

## Remaining boundaries

M3–M6 remain pending. Authentication uses local bearer credentials; TLS,
rotation, rate limiting, production identity, pagination and retention policies
are future work. Escalations can be listed but M2 does not implement operator
resolution workflows. Transactions span model latency and have no distributed
work queue. No Kafka/outbox, Angular, Airflow or deployment is included.

The dependency audit reports nine moderate entries propagated from one
`hyperid` → `uuid@8` advisory in LoopBack's dependency graph. No high/critical
findings remain after compatible `undici` and busboy overrides. A blanket forced
LoopBack downgrade is not applied. Track the remaining upstream fix before
production deployment; this milestone is a loopback-only synthetic demo.
